## Context

Classic `jekyll-paginate` (whitelisted by the `github-pages` gem) paginates every post in `site.posts` as one global, language-blind sequence, sliced by `paginate: 8`. Both home pages currently work around this by abandoning pagination entirely (`translate-english-posts-to-portuguese`'s stopgap): `index.html` and `pt/index.html` both override `articles.data_source: site.posts`, rendering every post on a single page, and `_includes/paginator.html` was given a guard to suppress its now-meaningless "N posts, M pages" widget on those two pages. That's correct today but doesn't scale as more posts accumulate in either language.

Research for this proposal found `jekyll-paginate-v2` (`sverrirs/jekyll-paginate-v2`) has first-class support for exactly this case: a pagination page's front matter can set `pagination.locale: <value>`, and the plugin filters `site.posts` (or a named collection) down to only posts whose own `locale` front-matter field matches, before paginating that filtered set. It also aims for backward compatibility with classic `jekyll-paginate`'s `paginator` object shape (`paginator.posts`, `.total_pages`, `.page`, `.previous_page`, `.next_page`, etc.), which is what `_includes/paginator.html` already consumes.

Separately, this proposal's research found that `actions/jekyll-build-pages` (the current `build` job step) ships its own `github-pages`-gem environment baked into its Docker image at the time the *action itself* was published, and only ever reads this repository's `Gemfile` to print a compatibility warning (`bundle check --dry-run`) — it never actually `bundle install`s or builds against it. Confirmed by reading the action's own `entrypoint.sh`. This means the repo's committed `Gemfile.lock` has never actually been what the CI build installs from, and adding `jekyll-paginate-v2` to the `Gemfile` alone would have zero effect unless the build step itself changes too.

## Goals / Non-Goals

**Goals:**
- Restore real, multi-page pagination to both home pages, each correctly scoped to its own language (English posts only for `/`; every post, with the existing dedup/fallback rules, for `/pt/`).
- Make the build actually install and run from this repository's own `Gemfile`/`Gemfile.lock`, so `jekyll-paginate-v2` (and any future dependency change) takes effect for real.

**Non-Goals:**
- No change to archive/tag-search scoping (`_includes/article-list.html`'s existing `_page_lang`/`translation_key` dedup logic) — those already work correctly per-page and aren't paginated by the plugin today; only the two home pages are in scope.
- No attempt to preserve compatibility with GitHub's classic (non-Actions) Pages builder — this repo already only deploys via the `deploy.yml` Actions workflow (per `add-github-actions-deploy`), so there is no classic-builder compatibility to protect.
- No visual/design change to the pagination widget beyond what's needed to reflect correct per-language counts again (removing the stopgap guard added in `translate-english-posts-to-portuguese`).

## Decisions

**Build step**: replace the `build` job's `actions/jekyll-build-pages` step in `.github/workflows/deploy.yml` with an explicit `ruby/setup-ruby` (with `bundler-cache: true`, so it installs from and validates against this repo's own `Gemfile.lock`) followed by `bundle exec jekyll build --destination ./_site`. The `deploy` job and `actions/deploy-pages` step are unaffected — they only consume whatever static files land in the uploaded artifact, regardless of how the build step produced them.

**Gemfile**: replace `gem "github-pages"` with `gem "jekyll"` (pinned to a specific version compatible with the theme and current Ruby) and add `gem "jekyll-paginate-v2"`; move any other plugins the site actually uses (checked against the current `Gemfile.lock`) from the `github-pages` metagem's implicit set to explicit `gem` lines, since they're no longer pulled in transitively.

**Locale field for the plugin's filter**: `jekyll-paginate-v2`'s locale filter reads a post's own `locale` front-matter field (a fixed field name, not configurable). Rather than introduce a second, separate language concept alongside the existing `lang` field, populate `locale` with the same value as `lang` via the same `_config.yml` `defaults:` scopes that already set `lang` (root `_posts` scope → `locale: en`; `_posts/pt` scope → `locale: pt-BR`) — no per-post front-matter duplication needed, and no existing template logic (which all keys off `lang`) needs to change.

**Per-page pagination config**: add a site-wide `pagination:` block to `_config.yml` (`enabled: true`, `per_page: 8` matching today's `paginate: 8`, `permalink: '/page:num'` matching today's `paginate_path`, `sort_field: date`, `sort_reverse: true`). Give `index.html` a `pagination: { locale: en }` front-matter override, computed and correct by construction since English's own listing rule is a plain `lang == 'en'` filter with no dedup logic.

**Solving Portuguese pagination too** (owner decision: solve both languages now, not just English): `jekyll-paginate-v2`'s `locale` filter is a single-field equality match and can't by itself express the Portuguese listing's actual rule ("every post, except an English post whose `translation_key` already has a Portuguese sibling"). Moving the build off `actions/jekyll-build-pages`'s restricted, whitelist-enforced environment (this proposal's other half) removes the constraint that previously ruled out a solution here too: with a plain, self-managed `bundle exec jekyll build`, this repository can also load its own small custom Jekyll plugin from `_plugins/` (not possible under the old `github-pages`-gem-wrapped build, which runs in Jekyll's restricted `safe` mode that disables custom plugins entirely).

So: add one small custom generator plugin (e.g. `_plugins/pt_listing_tag.rb`) that runs before `jekyll-paginate-v2`'s own generator and computes, for every post, whether it belongs in the Portuguese listing — mirroring exactly the dedup/fallback rule `_includes/article-list.html` already computes in Liquid (a Portuguese post always belongs; an English post belongs only if no Portuguese post shares its `translation_key`) — and tags qualifying posts with a synthetic Jekyll category (e.g. `pt-listing`). `pt/index.html`'s pagination front matter then becomes `pagination: { category: 'pt-listing' }`, giving it real, correctly-scoped multi-page pagination too. Because the tag is computed at build time from the same `translation_key`/`lang` relationships the Liquid logic already uses (not hand-maintained per post), it can't drift out of sync the way a manually-curated category list could.

**`_includes/paginator.html`**: remove the `translate-english-posts-to-portuguese` stopgap guard (`_page_articles_source != 'site.posts'`) on both pages now that each `paginator` object is correctly per-language by construction; the existing custom `_post_count`/dedup-counting loop becomes unnecessary for both pages (the plugin's own `paginator.total_pages`/post list are already scoped) and can be simplified back to `paginator.posts.size`-style logic, though the per-page-type language check should stay as a defensive assertion during rollout.

## Risks / Trade-offs

- [Moving off `actions/jekyll-build-pages` means this repo now owns Ruby/Jekyll/plugin version compatibility that GitHub previously managed] → Pin exact versions in `Gemfile`/`.ruby-version`; the PR-build check (already required by `site-build-pipeline`) catches incompatibilities before merge, same safety net as today.
- [A custom Jekyll plugin is more moving parts than a pure-config plugin filter, and its logic must be kept conceptually in sync with `article-list.html`'s Liquid dedup rule even though they're written in two different languages] → Keep the plugin intentionally small (one generator, one computed tag) and covered by the same real-build PR verification already required for every change in this repo; note the duplication explicitly in the plugin's own comments so a future edit to one side prompts checking the other.
- [Gemfile.lock will need full regeneration against `jekyll` instead of `github-pages`] → Expected; verify via a real PR build (per `site-build-pipeline`'s existing requirement) before merging, same practice used throughout this project's prior changes.
